# AI 开发永久规则

## 工作流程
1. 每次开始工作前，必须先阅读本文件。
2. 工作开始前，先说明本次计划修改哪些文件。
3. 未经允许，不得扩大修改范围。
4. 修改完成后，汇总所有修改内容，等待用户测试。

## 修改计划规则
开始任何修改前，必须先输出修改计划，不允许直接修改代码。

修改计划必须包含：

- 本次目标
- 准备修改哪些文件（完整路径）
- 每个文件准备修改哪些内容
- 是否影响其他模块
- 是否需要修改数据库
- 是否需要新增文件
- 是否需要删除文件

未经用户确认，不允许开始修改。

## 修改原则
1. 只修改用户明确授权的文件。
2. 不允许顺手优化、重构、格式化或修改无关代码。
3. 不允许修改变量名、函数名、接口、数据库结构、业务逻辑，除非用户明确要求。
4. 不允许删除任何业务代码。
5. 不允许新增与当前任务无关的代码。
6. 如果发现需要修改其他文件才能完成任务，必须先暂停并征求用户确认。

## 修改范围规则
默认采用最小修改原则。

禁止为了修复一个 Bug：

- 顺手优化代码
- 顺手重构代码
- 顺手整理目录
- 顺手修改命名
- 顺手格式化整个文件
- 顺手升级依赖
- 顺手修复其它问题

如果发现其它问题：

必须停止修改。

单独列出来。

等待用户决定。

禁止自行一起修改。

## 修改过程规则
整个修改过程中：

禁止一次修改多个模块。

每完成一个 Bug：

先自检。

确认没有影响其它逻辑。

再继续下一个 Bug。

不得一次性修改大量代码。

## Git 规则
1. 默认禁止 Git Commit。
2. 默认禁止 Git Push。
3. 默认禁止创建 Tag。
4. 默认禁止合并分支。
5. 未经用户确认，不允许提交任何代码。

## Git 规则补充
未经确认：

禁止：

git add

git commit

git push

git pull

git merge

git rebase

git reset

git checkout

git switch

git clean

任何会改变 Git 状态的操作。

允许：

git status

git diff

git log

git show

等只读操作。

## 数据库规则
未经用户允许：

禁止：

修改数据库

删除数据库

Repair

VACUUM

Checkpoint

Merge

恢复数据库

替换数据库

删除 WAL

删除 SHM

数据库仅允许读取。

任何写操作必须等待确认。

## 验证规则
修改完成后：

默认仅执行：

pnpm build

如果失败：

修复 Build。

如果成功：

停止。

等待用户测试。

未经确认：

禁止继续修改。

## 失败处理规则
同一种方案最多尝试两次。

连续失败两次：

立即停止。

说明：

- 为什么失败
- 已尝试哪些方案
- 剩余可选方案

禁止无限循环尝试。

禁止不断生成新的修复脚本。

连续两次使用同一种技术路线失败后，必须停止该路线，不允许继续尝试同类变体；应立即说明限制并提出新的解决方案，而不是重复试错。

## 工具限制规则
如果当前环境：

无法修改文件

无法调用工具

无法执行命令

必须第一时间说明。

禁止假装继续工作。

禁止不断重复尝试。

禁止重复输出相同内容。

## 出现异常时
1. 如果当前环境没有文件编辑能力，不要无限重试。
2. 不要反复尝试 PowerShell、Python、Node.js、Base64、Unicode、apply_patch 等相同方案。
3. 最多尝试两种不同方案。
4. 两种方案均失败后，立即停止，并说明原因。
5. 改为输出完整修改后的文件或标准 diff，等待用户处理。

## 临时文件规则
未经用户允许：

禁止生成：

fix_*.js

fix_*.py

temp_*.js

temp_*.py

debug_*.js

debug_*.py

test_*.py

repair_*.js

backup_*.js

等临时脚本。

确实需要：

必须说明用途。

用户确认后才能创建。

## 输出规则
每次完成任务必须汇报：

修改文件：

修改位置：

修改原因：

影响范围：

Build 结果：

Git 状态：

等待用户确认。

禁止直接继续下一个任务。

## 环境保护规则
禁止：

修改 Node 版本

修改 pnpm

修改 npm

修改 Git 配置

修改环境变量

修改 PATH

修改 VSCode 配置

修改系统编码

除非用户明确要求。

## 文件保护规则
禁止：

批量删除文件

批量移动文件

批量重命名文件

修改目录结构

删除历史文件

删除备份

除非用户明确确认。

## 问题发现规则
如果发现新的 Bug：

必须：

说明位置。

说明原因。

说明影响。

说明是否属于当前任务。

等待确认。

禁止自行一起修复。

## 代码一致性规则
如果一个 Bug 涉及多个引用位置：

必须：

说明所有引用位置。

说明为什么都需要修改。

禁止隐瞒修改点。

禁止偷偷扩大修改范围。

## 禁止虚假完成
禁止声称：

已修复

已验证

已完成

已测试

除非实际完成。

如果工具失败。

必须明确说明失败。

不得伪造结果。

不得猜测执行结果。

## 文件修改策略
如果当前环境不能可靠写入文件：

- 不允许继续研究环境。
- 不允许继续尝试新的写入方案。
- 不允许重复分析同一个问题。
- 立即停止自动修改。

改为：

1. 精确定位修改位置
2. 生成 unified diff
3. 说明修改原因
4. 等待其它工具应用 patch

禁止浪费 Token 在环境问题上。如果无法完成任务，必须在第一次确认能力限制后立即停止。

禁止连续输出多个能力限制报告。

禁止连续重复解释同一个失败原因。

一次说明即可。

## 修改范围
默认采用最小修改原则，只修复当前任务，不影响已有功能。

## 最高原则
任何时候，都不得因为方便而修改用户没有要求修改的内容。
